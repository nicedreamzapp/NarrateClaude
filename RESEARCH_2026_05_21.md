# NarrateClaude — Barge-In Research, 2026-05-21

Author: Claude (research pass for Matt) · Host: M5 Max 128 GB · macOS 26.4.1 (25E253)

## TL;DR

- **The most likely root cause of tonight's "all blank" failure is not VPIO over-suppression — it's that the v2 engine is configured at 48 kHz mono Float32, which is _exactly_ the misconfiguration that has been documented for years as making the macOS VPIO audio unit emit "stream has been all zeros for 10 seconds" or near-silent buffers.** Multiple sources (Apple forums thread 66953, OpenAI Realtime "audio notes for Apple platforms" thread) say VPIO on macOS is happiest at 44_100 Hz, with the device's native hardware rate matched on both scopes, and that mismatched stream formats are the leading cause of silent input from VPIO even when the engine starts cleanly. The Phase 1 "format fix" in `AudioEngine.swift` only fixed the player→outputNode side; the input side is still being asked to deliver at a foreign rate.
- **There is a separate, concurrent macOS 26 (Tahoe) Core Audio regression that returns all-zero mic samples for some USB-class devices, but it does not appear to affect the built-in MacBook Pro Microphone**, and Apple has been actively patching audio bugs across 26.1/26.2 (Rogue Amoeba enumerated several). So this is unlikely to be your bug, but it is worth a sanity check: the issue is real and ongoing in 26.x.
- **Shortest path to a working v2 tonight: ship "v2 minus VPIO."** Disable `setVoiceProcessingEnabled(true)` behind a build flag, keep everything else (FluidAudio Silero VAD + WhisperKit + Smart Turn v3 + Piper through the engine's player node) and accept that barge-in degrades to Attempt-3 behavior (skip mic feed while TTS plays). You retain the EOT + cleaner architecture wins of v2; you give up the personal-VAD-conditioned barge-in for now. This unblocks the publishable Phase 3 work — synthesizing the training corpus does not require VPIO to be live.

## Q1 — macOS 26 (Tahoe) VPIO regressions

**Verdict: There are real Tahoe Core Audio regressions, but the "VPIO ducks the mic to silence" symptom we are seeing is more likely caused by stream-format misconfiguration than by an OS bug.**

Three concrete findings:

1. Rogue Amoeba's audit of 26.0 → 26.1 explicitly enumerated audio bugs Apple shipped and then patched: FaceTime/Phone capture failures, sample-rate mismatch failures when secondary outputs differed from the primary device, low-sample-rate capture regressions, and an "overly aggressive low-pass filter" the system was applying to captured audio. The low-pass filter detail is interesting in our context — if Apple is filtering above ~10 kHz at the capture path on top of VPIO's own noise suppression, your peak/RMS would still look low to WhisperKit. ([weblog.rogueamoeba.com 2025-11](https://weblog.rogueamoeba.com/2025/11/04/macos-26-tahoe-includes-important-audio-related-bug-fixes/))

2. Apple-side voice-isolation "Mic Modes" introduced in Sonoma 14 are still on macOS 26 and **remove frequencies above 10 kHz** from the input channel when active. This applies system-wide, independent of VPIO. ([Focusrite Sonoma/Sequoia/Tahoe input issues](https://support.focusrite.com/hc/en-gb/articles/15437020104082); [UA "Mic Mode" silence/garble](https://help.uaudio.com/hc/en-us/articles/26704705384980))

3. A confirmed 26.0/26.1 USB-Audio-Class regression returns all-zero samples for some USB-class devices (Reachy Mini reproduced via sounddevice/PortAudio + ffmpeg + AVFoundation). Built-in mic is **not** in the affected set per that issue's reproduction matrix. ([reachy_mini #820](https://github.com/pollen-robotics/reachy_mini/issues/820))

The Apple Developer forum thread "AVAudioEngine input giving silence" turned out to be a sandbox-entitlement bug — irrelevant since `talkingstick` runs unsandboxed. ([Apple DevForum 771048](https://developer.apple.com/forums/thread/771048))

The more interesting Apple thread is "Volume issue when Voice Processing IO enabled" — it documents that VPIO actively ducks _other_ audio sources when running and that this has persisted from iOS 13 through 16+ with no Apple acknowledgement. So the "VPIO ducks the world" behavior is real and not Tahoe-specific. ([Apple DevForum 721535](https://developer.apple.com/forums/thread/721535))

## Q2 — Alternative AEC paths

**Verdict: stay on Apple VPIO, but configure it correctly via low-level CoreAudio AudioToolbox, not via `AVAudioEngine.setVoiceProcessingEnabled(true)`.**

The single most useful citation in this whole search:

> **"Lower-level AudioToolbox direct audio unit management proved more reliable than `AVAudioEngine` abstractions. One developer successfully implemented this [OpenAI Realtime on Apple platforms] with reported 'buttery smooth' audio quality."**
> ([OpenAI community: audio notes for OpenAI realtime on Apple platforms](https://community.openai.com/t/audio-notes-for-openai-realtime-on-apple-platforms/1108404))

Same thread points out:
- **VPIO on macOS prefers 44100 Hz initialization** — using 48000 Hz forces a resampler insertion that has historically broken VPIO init or yielded silence.
- **Initialize `AVAudioEngine` real-time playback _before_ instantiating the VoiceProcessingIO unit.** Reversing the order ducks playback. Our v2 enables VPIO first thing in `init()` — that's the opposite order.
- Disable the output scope of element 0 on the VPIO unit to silence iOS render-error log spam.

The Apple DevForum 66953 thread confirms VPIO works on macOS only via the **callback-based API**, not via `AUGraph` or declarative connections, and that I/O is enabled by default and `kAudioOutputUnitProperty_EnableIO` returns `-10865 kAudioUnitErr_PropertyNotWritable` on VPIO. ([Apple DevForum 66953](https://developer.apple.com/forums/thread/66953))

WWDC23 session 10235 adds two relevant configuration properties that may be biting us right now even if VPIO is otherwise correct:
- `voiceProcessingOtherAudioDuckingConfiguration` (`enableAdvancedDucking`, `duckingLevel` with `.default | .min | .mid | .max`). v2 sets nothing → falls through to `.default`, which on macOS 26 may be the aggressive setting that is ducking the player node loud enough that the cleaned mic stream goes nearly silent every time TTS plays.
- `isVoiceProcessingAGCEnabled` — boolean to **disable AGC** on the cleaned mic. Defaults to true; for STT we almost certainly want it false so quiet speech does not get auto-leveled down when the system thinks it sees clipping from the TTS reference path.
([WWDC23: What's new in voice processing](https://developer.apple.com/videos/play/wwdc2023/10235/))

A working macOS VPIO callback-style reference is the standy66 gist — it uses 48 kHz mono Float32 successfully **but supplies the reference signal manually via the output render callback** rather than relying on VPIO to tap the HAL output. That is a critical distinction we got wrong in `EXPERIMENT_PLAN.md`: VPIO does **not** automatically tap the HAL output mix — you must give it the reference signal explicitly via the render callback on element 0. ([standy66 VPIO gist](https://gist.github.com/standy66/c8ac19ea1a05be0a5b62f45732a640d4))

This invalidates the Phase-1 premise. Connecting the player node to `engine.outputNode` does not give VPIO a reference signal — it just routes the audio through the same output device. VPIO's reference path is **the unit's own output render callback**, populated by the host. If `AVAudioEngine.setVoiceProcessingEnabled(true)` wires this up automatically, it does so via private internal plumbing we cannot inspect; the empirical evidence from this session says it does not.

Standalone AEC paths (rejection of Attempt 4 still stands):
- **WebRTC AEC3** has no maintained Swift wrapper. The 2024–2026 attempts to package it for SPM have all stalled. Still ~250 lines of C++ glue.
- **Speex AEC** is simpler (one C file) but only handles narrowband and would require us to downsample TTS reference to 8 or 16 kHz with explicit time alignment.
- **Picovoice Koala / NS** is closed-source for revenue use.

Verdict: low-level AudioToolbox VPIO is still the right primitive; we just used the wrong wrapper.

## Q3 — How Pipecat does this on Mac

**Verdict: Pipecat ships Smart Turn + Silero VAD but punts echo cancellation to either headphones, WebRTC's browser-side AEC, or a future feature.**

- Pipecat issue [#188 "Interrupted by itself when speaker on"](https://github.com/pipecat-ai/pipecat/issues/188) — open, no fix offered, recommendation in adjacent threads is "use headphones."
- Pipecat issue [#670 "Echo cancellation"](https://github.com/pipecat-ai/pipecat/issues/670) — open since 2024, no roadmap.
- [kwindla/macos-local-voice-agents](https://github.com/kwindla/macos-local-voice-agents) is the Pipecat-on-Mac reference. It uses Silero VAD + MLX Whisper + Kokoro TTS via local serverless WebRTC. The WebRTC transport is what gives it AEC — the browser's audio capture pipeline runs Chrome's WebRTC AEC3 before the audio ever reaches Python. Without the WebRTC client, the reference design has no AEC.
- [dusterbloom/localcat](https://github.com/dusterbloom/localcat) similarly leans on WebRTC for AEC.

So Pipecat's "barge-in on Mac" story is actually: **WebRTC AEC3 in the browser, not native AEC on macOS.** That confirms what we found in Attempt 4 — but with a twist: instead of porting WebRTC AEC3 to a Swift package, we could host the audio capture in Chromium (e.g. an Electron shell or a WKWebView with the right entitlements) and let the OS's bundled WebRTC do the AEC.

That's a much cheaper path than porting AEC3 — but it adds a browser to the stack, which is exactly the architectural rot we are trying to avoid.

## Q4 — OpenAI Realtime barge-in

**Verdict: OpenAI offloads AEC to the browser (WebRTC) on web clients, and to the OS audio session on native iOS apps. There is no special sauce.**

- [openai/openai-realtime-console](https://github.com/openai/openai-realtime-console) uses WebRTC, which gets browser-side AEC3 for free.
- The OpenAI dev community thread [Audio notes for OpenAI realtime on Apple platforms](https://community.openai.com/t/audio-notes-for-openai-realtime-on-apple-platforms/1108404) (cited above) documents that native iOS/macOS clients use VPIO via lower-level AudioToolbox, with 44.1 kHz init and pre-VPIO engine setup.
- VAD-triggered interruption (server-side): when OpenAI Realtime's server VAD detects user speech, it cancels the in-flight assistant response. **That is just a cancel-the-stream operation, not AEC.** It only works because the client's AEC already cleaned the mic before sending.

So OpenAI's barge-in story for browser users is "WebRTC AEC handles it" and for native users is "VPIO via direct AudioToolbox handles it."

## Q6 — sherpa-onnx / Moshi / OpenVoice / Ultravox barge-in on Apple Silicon

**Verdict: sherpa-onnx is the closest fit for incremental ASR with VAD on Apple Silicon today, but none of these projects ship working open-air barge-in. Moshi is the only true full-duplex option and runs on M3/M4 via MLX, with no public barge-in benchmark over speakers.**

- [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) supports Apple Silicon natively (Intel + aarch64), has streaming ASR + Silero VAD wired in [`vad-with-non-streaming-asr.py`](https://github.com/k2-fsa/sherpa-onnx/blob/master/python-api-examples/vad-with-non-streaming-asr.py). Recommendation: PyAudio non-blocking callback delegates to the PortAudio C thread so the GIL doesn't drop barge-in events ([sherpa-onnx mic example](https://k2-fsa.github.io/sherpa/onnx/python/real-time-speech-recongition-from-a-microphone.html)). No AEC in the pipeline — PortAudio just hands over raw input.
- [Moshi](https://github.com/kyutai-labs/moshi) MLX port exists ([Blaizzy/mlx-audio Moshi chapter](https://deepwiki.com/Blaizzy/mlx-audio/7.4-moshi-model)), runs on MacBook Pro M3 per the README. Quantizations (int4/int8/bf16) available. Theoretical 160 ms latency, 200 ms on L4 GPU — no Apple Silicon number published. Full-duplex by design — it _models_ both audio streams simultaneously, so barge-in is implicit in the architecture, but only if the input stream is clean.
- Ultravox / Mini-Omni / OpenVoice — none have a documented open-air barge-in implementation on Apple Silicon. They are either text-output-only speech LLMs or unidirectional TTS.

## Q7 — Joint full-duplex state of the art on M5 Max

**Verdict: Moshi (Kyutai) is the only viable option today. Mini-Omni 2 and Ultravox are speech-input → text-output; they don't do barge-in.**

- Moshi 7B fits comfortably in 128 GB unified memory at bf16 (~14 GB). 4-bit quantization brings it to ~4 GB.
- Apple's own ML research published the [M5 GPU neural accelerator benchmark](https://machinelearning.apple.com/research/exploring-llms-mlx-m5) showing **up to 4× speedup over M4 for time-to-first-token on LLM inference via MLX**, which is the exact bottleneck for Moshi's autoregressive decoder.
- LoRA fine-tuning Moshi on personal (user voice + Piper-clone TTS) pairs is feasible on M5; the limiting factor is training corpus size, not memory.
- Phase 5 of `EXPERIMENT_PLAN.md` is still the right north star. It is _not_ tonight's problem.

## Q8 — Pragmatic shortest path

**Verdict: ship v2 with VPIO behind a build flag, defaulted off.**

Concretely:

1. Add a `--no-vpio` flag or env var (`TS_DISABLE_VPIO=1`) to `talkingstick`.
2. When VPIO is disabled, skip `engine.inputNode.setVoiceProcessingEnabled(true)` entirely. The engine then captures raw mic at the device's native rate.
3. Re-enable the `speakIsPlaying` skip while TTS is playing — same defensive behavior as v1 Attempt 3.
4. Verify that WhisperKit + FluidAudio Silero VAD + Smart Turn v3 + Piper-via-player-node all work end-to-end without VPIO. **This is the test that wasn't run before declaring Phase 1 complete.**

This gives us:
- Working transcripts (v1 parity)
- Smart Turn EOT detection (new in v2)
- Cleaner architecture (TTS through the engine, not afplay)
- A scaffold to layer Phase 3 (personal VAD) on top of
- Zero barge-in (regression from the v1 goal, but v1 didn't actually have it either)

Then, **separately**, prototype the low-level AudioToolbox VPIO path as a Swift wrapper, get it working in a standalone test binary that ffplays the cleaned tap to disk, and only merge it into TalkingStick once the recorded WAV proves VPIO is suppressing only the playback, not Matt.

## Kill list (do not pursue further)

- **Porting WebRTC AEC3 to Swift Package Manager.** Confirmed (this session and last) that there is no maintained wrapper and no community demand to build one. Apple VPIO via low-level AudioToolbox is the correct primitive on this OS.
- **Hosting audio capture inside Chromium/WKWebView for free WebRTC AEC3.** Architectural rot. We are not shipping a browser shell to dodge one Apple bug.
- **Amplitude-based barge-in.** Already in the kill list. Stays there.
- **Speex AEC.** Narrowband; would have to throw away the high-frequency content WhisperKit benefits from. Not worth the work given Apple VPIO is one configuration fix away.
- **Tuning the WhisperKit hallucination filter list to be less strict.** Symptom-treatment. The right fix is upstream — get the mic stream actually carrying Matt's voice.
